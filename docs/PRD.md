# 多平台聊天记录聚合 App 产品需求文档

- 产品代号：待定
- 文档状态：已确定 iOS 先行 + KMP 共享核心策略 / V0.2
- 目标平台：iOS 优先发布；Android 为确定的后续目标，核心架构从第一天起保证可迁移
- 更新日期：2026-10-27

## 1. 产品定位

这是一个面向小情侣、闺蜜、挚友等强关系用户的私人聊天记忆库。它把同一个联系人在微信、QQ、小红书、抖音上的聊天记录，按时间合并成一条可全局搜索、可打标签、可回溯的统一时间线。

它不是第三方聊天客户端，初期也不追求替用户在各平台发送消息，而是专注成为聊天内容的**整理、检索、标注和回忆层**。

## 2. 目标用户与场景

### 2.1 目标用户

1. **小情侣**
   - 想保存异地聊天、约定、纪念日和日常梗。
   - 常见痛点：聊天内容分散，翻历史记录困难，重要约定被淹没。
2. **闺蜜 / 挚友**
   - 共同追星、种草、旅行计划、吐槽和待办事项。
   - 常见痛点：链接、图片、视频、语音和文字分散在不同平台。

### 2.2 核心场景

- **回忆搜索**：“他之前说过不吃香菜，到底在哪说的？”
- **约定整理**：把“明年一起去京都”“周五看展”标成约定，形成共同待办。
- **跨平台回看**：某天微信、小红书、抖音都聊过同一件事，希望看到统一时间线。
- **礼物和喜好沉淀**：通过标签整理对方提过的喜好、尺码、忌口、想要的物品。
- **内容回跳**：从小红书/抖音转发来的帖子，可以快速跳回原帖查看最新评论和内容。

## 3. 产品目标

### 3.1 北极星指标

**每周有效搜索次数 / 活跃用户**：衡量用户是否真的把产品当作记忆检索工具，而不是一次性导入工具。

### 3.2 辅助指标

- 首次导入成功率
- 7 日、30 日留存率
- 人均标签数量
- 跨平台联系人绑定数量
- 从搜索结果进入聊天详情的转化率
- 从小红书/抖音消息成功跳回原帖的比例

## 4. MVP 范围

### 4.1 必须做

1. **本地身份与联系人绑定**
   - 用户创建一个 App 内联系人。
   - 先绑定微信身份。
   - 再手动绑定同一人的 QQ、小红书、抖音身份。
   - 支持一个 App 内联系人对应多个平台账号。
2. **聊天记录导入**
   - 支持用户主动导入聊天记录文件或截图。
   - 初期优先探索微信/QQ 可用导出格式。
   - 小红书、抖音先支持消息元数据与链接导入，不承诺完整记录抓取。
3. **统一时间线**
   - 按消息时间排序。
   - 每条消息展示平台、发送者、时间、正文、媒体占位、原帖链接。
   - 使用不同颜色和图标区分微信、QQ、小红书、抖音。
4. **全局文本搜索**
   - 支持超快本地全文搜索。
   - 支持联系人、平台、时间范围、标签、关键词组合过滤。
   - 搜索结果高亮命中词。
5. **标签系统**
   - 内置标签：食物爱好、TODO、约定一起要做的事。
   - 支持自定义标签、标签颜色、备注。
   - 支持按联系人查看标签云或标签分组。
6. **原帖跳转**
   - 对可识别的小红书/抖音链接提供“打开原帖”。
   - 不在 MVP 中强依赖登录第三方平台。

### 4.2 暂不做

- 替用户向第三方平台发送消息。
- 未经授权抓取第三方平台数据。
- 云端多人协作和共享记忆库。
- 图片 OCR、语音转文字、智能摘要。
- 自动识别同一个人。
- Android 端正式发布。

说明：Android 不进入 MVP 交付范围，但不是“以后再考虑”的模糊目标。MVP 必须采用跨平台核心架构，避免联系人绑定、导入、去重、搜索、标签等核心规则被锁死在 iOS 代码中。

## 5. 用户流程

### 5.1 首次使用

1. 创建本地密码或启用 Face ID / Touch ID。
2. 创建联系人，例如“小 A”。
3. 选择微信作为主身份，填写或选择备注名。
4. 导入微信记录。
5. 系统解析出候选聊天对象，由用户确认。
6. 继续为小 A 绑定 QQ、小红书、抖音身份。
7. 导入对应平台数据。
8. 进入统一时间线，系统提示可用搜索和标签功能。

### 5.2 绑定多个平台身份

- 用户始终拥有最终确认权。
- 每次绑定需选择：平台、平台昵称/备注、账号标识、默认头像颜色。
- 绑定后可设置合并优先级：例如头像以微信为准，昵称以微信为准。
- 若同一平台有多个账号，例如两个微信号，也允许并列绑定。

### 5.3 搜索与打标签

1. 用户在首页下拉或点击搜索入口。
2. 输入“香菜”。
3. 结果展示所有命中消息，并标注来源平台。
4. 用户选中一条或多条消息。
5. 点击添加标签“食物爱好”，补充备注“不吃香菜”。
6. 在联系人详情页查看“食物爱好”标签集合。

## 6. 功能需求

### 6.1 平台来源标识

| 平台 | 主色建议 | 初期数据能力 | 内容跳转 |
|---|---:|---|---|
| 微信 | 绿色 | 聊天记录文件/截图导入，身份用户确认 | 尽量支持上下文查看 |
| QQ | 蓝色 | 聊天记录文件/截图导入，身份用户确认 | 尽量支持上下文查看 |
| 小红书 | 红色 | 消息、链接、帖子元数据导入 | 支持跳转原帖 |
| 抖音 | 黑色/青色 | 消息、链接、视频元数据导入 | 支持跳转原帖 |

### 6.2 统一时间线

要求：

- 时间采用统一时区存储，展示时按手机系统时区。
- 消息按时间升序/降序可切换。
- 相邻同平台、同发送者消息可分组显示。
- 每条消息保留：
  - 平台
  - 原始聊天对象标识
  - 发送者类型：我 / 对方 / 系统
  - 原始时间戳
  - 正文
  - 媒体文件引用
  - 外部链接
  - 导入批次
  - 解析置信度
- 无法确认精确时间时，显示“时间待确认”，不能伪造。

### 6.3 全局搜索

搜索必须做到“超级灵敏”，目标为本地百万级消息文本查询进入 100ms 内的可用响应。

功能要求：

- 默认全局搜索。
- 支持搜索语法：
  - `person:小A 香菜`
  - `platform:微信 香菜`
  - `tag:食物爱好`
  - `after:2026-01-01 before:2026-10-27`
  - `"不吃香菜"` 精确短语
- 支持拼音、大小写英文、中文分词。
- 支持最近搜索、保存搜索、结果内筛选。
- 支持按相关度和时间排序。
- 搜索过程中不向服务器发送明文聊天内容。

### 6.4 标签系统

对象层级：

- 消息标签：一条或多条消息。
- 联系人事实：从消息中沉淀出的结论，例如“不吃香菜”。
- 共同事项：TODO、约定、旅行计划。

字段建议：

- 标签名称
- 颜色
- 类型：普通标签 / TODO / 约定 / 偏好
- 状态：未开始 / 进行中 / 已完成 / 已取消
- 截止日期，可选
- 关联消息
- 用户备注

内置标签：

1. 食物爱好
2. TODO
3. 约定一起要做的事
4. 旅行计划
5. 礼物灵感

### 6.5 内容查看与跳转

MVP：

- 解析消息中的外部链接。
- 小红书、抖音消息保留原帖链接，支持系统打开。
- 对无法内嵌展示的内容，显示链接卡片、平台图标和导入摘要。

后期：

- 内嵌网页查看。
- 保存原帖快照，避免帖子删除后无法回看。
- 提示用户登录第三方平台存在账号和安全风险，必须显式选择。
- 不保存第三方登录凭证，除非完成独立安全设计与可撤销授权。

### 6.6 同步能力

产品目标是“那边聊完，这边立刻有”，但受 iOS 沙盒、第三方 App 数据隔离和平台条款限制，实时同步无法作为 MVP 承诺。

分阶段方案：

1. **手动导入**：用户主动选择文件、截图或分享内容。
2. **半自动更新**：用户打开 App 后触发增量导入，系统通过导入批次去重。
3. **提醒更新**：基于上次导入时间提醒用户更新。
4. **可控同步探索**：仅在平台提供官方能力、用户明确授权且合规时实现。

任何情况下都不采用隐蔽抓取或绕过系统安全机制。

## 9. 技术方案建议

### 9.1 总体架构决策

采用 **Kotlin Multiplatform Shared Core + 原生 iOS UI**：

```text
iOS App / SwiftUI
Android App / Jetpack Compose，后续
        ↓
KMP Shared Core
    ├── Person / PlatformIdentity / Message / Tag / Fact
    ├── Importer Adapter 接口与通用解析流程
    ├── 平台身份绑定规则
    ├── 时间线合并
    ├── 去重
    ├── 搜索语法解析
    ├── 标签与 Fact 逻辑
    └── 备份文件格式
        ↓
SQLite / FTS 索引
```

选择原因：

1. 当前目标是先发布 iOS MVP，同时 Android 是确定需求。
2. 本产品的长期价值主要在数据导入、统一检索、标签沉淀和备份，而不只在 UI。
3. SwiftUI 适合做高质量 iOS 界面，但不适合直接复用到 Android。
4. KMP 允许 iOS 先使用 SwiftUI，同时把领域逻辑、数据模型和搜索规则放入共享模块。
5. 后续 Android 使用 Jetpack Compose 接入同一核心，只重写 UI 与平台适配，不重写全部产品逻辑。

### 9.2 iOS 客户端

- UI：SwiftUI
- 通过 KMP 产物接入共享领域层
- 本地数据库：优先由共享层统一使用 SQLDelight / SQLite，避免 iOS 独自形成第二套业务数据库逻辑
- 全文索引：SQLite FTS5；中文可用内置分词加自定义分词补丁，或接入本地分词库
- 搜索响应：输入防抖 80ms～120ms，立即返回缓存结果
- 本地加密：SQLCipher 或 iOS Data Protection
- 备份：文件加密导出，优先不自动上云

### 9.3 Android 迁移策略

Android 正式启动时：

- UI 使用 Jetpack Compose。
- 直接接入 KMP Shared Core。
- 不重新定义 Person、Message、Tag、Fact 等核心模型。
- 不重写搜索语法、去重规则、时间线合并、标签状态机。
- 使用 Android 平台适配实现文件选择、系统分享、OCR、生物识别和外部链接跳转。

### 9.4 平台适配层

共享层定义接口，iOS 与 Android 各自实现：

| 能力 | iOS 适配 | Android 适配 |
|---|---|---|
| 文件导入 | `fileImporter` / Files App | Storage Access Framework |
| 系统分享接收 | Share Extension | Share Intent |
| OCR | Vision Framework | ML Kit |
| 隐私锁 | Face ID / Touch ID | Biometric API |
| 原帖跳转 | Universal Links / custom scheme | App Links / Intent |
| 安全存储 | Keychain / Data Protection | Keystore / EncryptedSharedPreferences |

注意：平台差异不只是聊天记录来源。导入路径、权限、分享入口、OCR、后台限制和外部 App 唤起都需要单独适配。

### 9.5 解析层

- 每个平台一个 Importer Adapter。
- 导入流程统一为：
  1. 选择来源
  2. 读取文件/截图/分享数据
  3. 抽取消息
  4. 疑似联系人候选
  5. 用户确认
  6. 去重入库
  7. 更新索引

Importer 分为两层：

1. **共享解析层**：解析文本、时间、发送者、链接、媒体引用和平台元数据。
2. **平台接入层**：iOS / Android 各自负责拿到原始文件或分享数据。

这样同一个微信记录解析器应尽量同时服务 iOS 与 Android；只有取文件的入口不同。

### 9.6 去重策略

- 以 `platform + chat_key + sender + timestamp + normalized_text + media_hash` 生成摘要。
- 对同一秒多条消息加入序号或上下文指纹。
- 对截图导入消息标注低置信度，允许用户合并重复。

## 10. 隐私、安全与合规

### 10.1 原则

- 默认本地存储。
- 不销售、不共享聊天数据。
- 不上传明文聊天内容。
- 用户可随时删除联系人、平台身份、导入批次和全部数据。
- App 内设置独立隐私锁。

### 10.2 第三方数据风险

微信、QQ、小红书、抖音没有面向第三方聊天记录聚合的完整开放 API。iOS 沙盒也限制 App 直接读取其他 App 数据。因此必须避免承诺“无感实时同步”。

可行方向：

- 用户主动导出并导入。
- 用户主动分享聊天文件、文本、链接或截图。
- 官方接口若未来可用，再申请授权。

### 10.3 App Store 风险

需重点评估：

- 数据抓取描述与隐私标签。
- 是否诱导用户绕过平台限制。
- 社交 App 登录与账号授权规则。
- 云端备份是否默认关闭。
- 敏感照片、聊天截图和 OCR 数据的处理说明。

## 11. 路线图

## 12. 实验与验证计划

### 12.1 用户访谈问题

1. 你最近一次想找某句聊天记录时，花了多久？
2. 你通常在哪些平台和同一个人聊天？
3. 哪类信息最值得沉淀：喜好、约定、链接，还是回忆？
4. 你能接受手动导入吗？多久更新一次？
5. 聊天记录保存在本地和上传云端，你更信任哪种？

### 12.2 原型验证

- 用 Figma 做三屏测试：时间线、搜索、标签。
- 招募 10～15 对目标用户。
- 衡量用户能否在 30 秒内完成一次跨平台搜索。
- 衡量用户是否愿意手动导入一次真实数据。

## 13. 开放问题

1. 微信和 QQ 的记录导入在 iOS 上最稳定、最合规的用户操作路径是什么？
2. MVP 是否先聚焦一对联系人，而不是支持大量联系人？
3. 截图 OCR 和文本文件导入哪个优先？
4. 标签是否需要支持层级，例如“旅行 / 日本 / 2027 春假”？
5. 数据备份是否完全交给用户，还是提供加密 iCloud 备份？
6. 内嵌第三方网页会不会带来登录、Cookie 和账号安全问题？

## 14. 成功标准

MVP 达标条件：
